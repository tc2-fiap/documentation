# Descobertas

Notas sobre conceitos que surgiram durante a construção deste sistema distribuído e que valem a pena registrar — coisas que, no processo de explicar o "porquê" de uma decisão arquitetural (ver [`notes.md`](../spec/notes.md), em inglês), acabaram se revelando ideias mais antigas e mais consolidadas do que pareciam à primeira vista. Escrito no mesmo espírito de `base-project/docs/discovers/discover.md`, mas com base nas decisões deste sistema (Postgres, Kubernetes, RabbitMQ/MassTransit, cinco serviços independentes), e não nas do monolito de referência (MongoDB, Terraform, Azure).

## 1. O "Transactional Outbox" é um padrão de mensageria dos anos 2000, não um recurso do MassTransit

`OrderService.CreateAsync` publica o `OrderPlacedEvent` e insere a linha do `Order` dentro da mesma unidade de trabalho, contando com o outbox do MassTransit sobre EF Core para garantir que os dois sejam confirmados juntos ou nenhum dos dois seja (`notes.md` 15). Isso não é uma invenção do MassTransit — é o padrão **Transactional Outbox**, descrito pela primeira vez como solução nomeada para o clássico problema da "escrita dupla" (um serviço não consegue atualizar seu próprio banco de dados *e* publicar uma mensagem em um broker separado de forma atômica, sem uma transação distribuída) no livro *Enterprise Integration Patterns* (Hohpe & Woolf, 2003) — anos antes do RabbitMQ 1.0 ou de qualquer biblioteca de mensageria atual do .NET existir. A implementação do MassTransit é só uma versão bem executada de uma ideia antiga: gravar a mensagem de saída em uma tabela dentro da *mesma* transação de banco de dados da mudança de negócio, para que um processo separado a retransmita de forma confiável depois — a atomicidade é garantida pela própria transação do banco, não pelo broker.

## 2. "Consumidor idempotente" pega emprestada uma palavra da matemática com 150 anos, não um termo específico de mensageria

Todo consumidor de evento aqui é idempotente, com a chave em `OrderId` ou `UserId` (`instructions.md` §10). O padrão em si — **Idempotent Receiver** — está catalogado no mesmo livro *Enterprise Integration Patterns* citado acima, mas a palavra "idempotente" é anterior à computação: o matemático Benjamin Peirce a cunhou em 1870 (*Linear Associative Algebra*) para uma operação em que aplicá-la duas vezes dá o mesmo resultado que aplicá-la uma vez (`f(f(x)) = f(x)`). Um consumidor que reprocessa um `PaymentProcessedEvent` reentregue e termina exatamente no mesmo estado como se tivesse processado apenas uma vez é essa mesma ideia do século XIX, aplicada a uma reentrega do RabbitMQ em vez de uma operação algébrica.

## 3. `Result`/`Result<T>` é um nome mais simpático para algo que linguagens funcionais têm há décadas

Este projeto retorna `Result`/`Result<T>` para falhas esperadas (não encontrado, validação, conflito) e reserva exceções para falhas genuínas (regras rígidas). Essa separação — um tipo de retorno que pode ser "ok" ou "um problema esperado", em vez de lançar uma exceção — é o que linguagens funcionais chamam de mônada `Either`, presente em ML e Haskell muito antes do .NET existir. O nome mais chamativo pelo qual a maioria conhece essa ideia, **Railway Oriented Programming**, foi cunhado por Scott Wlaschin para a comunidade F# por volta de 2013 — em si só uma metáfora (dois trilhos paralelos, sucesso e falha, que nunca se cruzam) para a ideia bem mais antiga do `Either`, hoje popular o suficiente para aparecer em uma minimal API em C# sem que ninguém chame isso de "programação funcional".

## 4. Clean Architecture é Hexagonal Architecture com um nome novo, que é o DIP com um diagrama

Todo serviço aqui segue `Domain → Application → Infrastructure`, com as dependências apontando para dentro e `Endpoints` na camada mais externa (regras rígidas). Robert C. Martin batizou isso de **Clean Architecture** em um post de blog de 2012 (depois um livro, em 2017), mas a regra em si — camadas externas e voláteis (frameworks, bancos de dados, HTTP) dependem de camadas internas e estáveis (regras de negócio), nunca o contrário — é a **Hexagonal Architecture** de Alistair Cockburn, descrita em 2005, sete anos antes. E a própria regra de Cockburn é uma aplicação direta do **Dependency Inversion Principle**, o "D" do SOLID, formalizado pelo próprio Martin em 1994. Três nomes, uma embalagem cada vez mais específica da mesma ideia, ao longo de dezoito anos.

## 5. A cadeia `OrderPlaced` → `PaymentProcessed` é uma Saga — a de banco de dados de 1987, não um jargão de microsserviços

`OrdersAPI` publica o `OrderPlacedEvent`; `PaymentsAPI` reage e publica o `PaymentProcessedEvent`; `OrdersAPI` reage a isso e conclui o pedido como `Paid` ou `Failed` (`instructions.md` §8). Isso é uma **Saga**: uma transação de negócio que não pode ser uma única transação ACID porque atravessa serviços separados, então é dividida em uma sequência de transações locais. O termo vem de um artigo da ACM de 1987, de Hector Garcia-Molina e Kenneth Salem — décadas antes de "microsserviços" virar palavra. A única peça que a saga deste projeto não precisa: uma transação *compensatória*. Um pagamento `Rejected` não precisa desfazer nada, porque nada foi efetivamente confirmado em nome do comprador até o pedido realmente se resolver — a saga aqui tem um caminho de falha, só não tem um rollback.

## 6. Coreografia vs. orquestração é uma bifurcação com nome, não só "como o RabbitMQ funciona por acaso"

Nada coordena a cadeia `OrderPlaced`/`PaymentProcessed` a partir de um ponto central — cada serviço reage a eventos e decide seu próprio próximo passo. Isso é **coreografia**, um dos dois estilos padrão para coordenar um processo de negócio multi-serviço (o outro, **orquestração**, tem um coordenador dedicado dizendo explicitamente a cada participante o que fazer em seguida, mais próximo de um motor de workflow). Os dois são nomeados, comparados e debatidos longamente na literatura de microsserviços (ex.: *Microservices Patterns*, de Chris Richardson, 2018) — escolher um dos dois aqui não foi um padrão-padrão do RabbitMQ, foi tomar um lado de uma troca arquitetural já estabelecida: a coreografia continua simples enquanto a cadeia for curta (e é, aqui — dois saltos), e fica difícil de acompanhar no momento em que um terceiro ou quarto serviço precisar reagir ao mesmo evento; a orquestração adiciona um coordenador, mas mantém todo o fluxo legível em um único lugar quando o processo cresce demais.

## 7. `IPaymentGateway` é um Anti-Corruption Layer, o mesmo livro do Shared Kernel do `base-project`

`PaymentsAPI` nunca deixa o vocabulário de status próprio da AbacatePay ou do Mercado Pago vazar para além de `IPaymentGateway` — cada implementação traduz a resposta específica do seu provedor para o `PaymentProcessedEvent` próprio deste sistema (`instructions.md` §5). Isso é o **Anti-Corruption Layer** de Eric Evans, do mesmo livro de 2003, *Domain-Driven Design*, que batizou o padrão Shared Kernel já coberto pelo próprio documento de descobertas do `base-project` — uma fronteira que existe especificamente para que o modelo de um sistema externo nunca possa ditar a forma do seu próprio domínio.

## 8. Autenticação JWT via bearer é um padrão IETF do início dos anos 2010, não uma convenção específica de API REST

Todo serviço aqui valida o mesmo cabeçalho `Authorization: Bearer <token>`, emitido uma única vez pelo `users-api`. O JWT em si é a **RFC 7519** (2015); o esquema "Bearer" é a **RFC 6750** (2012), parte do framework OAuth 2.0 (**RFC 6749**, 2012). Nada disso está atrelado a microsserviços, Kubernetes, ou sequer a REST especificamente — é maquinário genérico de autenticação HTTP anterior a toda essa arquitetura em uma década.

## 9. O índice único parcial de `order_items` aplica uma regra de negócio do mesmo jeito que Codd disse, em 1970

Duas restrições no Postgres — um índice único comum e um *parcial* (`WHERE status <> 'Failed'`) — garantem que não haja item duplicado em um pedido e nem posse ativa duplicada entre pedidos (`notes.md` 52), reforçando a checagem em nível de aplicação que é inerentemente sujeita a corrida sob concorrência. Deixar o próprio banco de dados ser a autoridade sobre uma regra de integridade, em vez de confiar que todo caminho de código vai checar antes, é a ideia central do **modelo relacional** que E. F. Codd introduziu em 1970 — uma constraint nada mais é do que uma afirmação formal e aplicada sobre quais dados podem existir, e o banco aplicando isso atomicamente é exatamente o que uma teoria de 55 anos disse que um banco de dados deveria fazer.

## 10. Server-Sent Events é anterior ao WebSocket como padrão de navegador

`GET /api/orders/{id}/stream` envia o status do pedido via SSE em vez de fazer polling (`notes.md` 53). É fácil presumir que o WebSocket é a opção "antiga" de tempo real e o SSE uma alternativa mais nova e simples, feita para casos que não precisam de tráfego nos dois sentidos — é o contrário. As raízes do `EventSource`/SSE estão nos rascunhos do HTML5 de meados dos anos 2000, e ele já era implementado nos navegadores anos antes do protocolo WebSocket sequer ser padronizado como **RFC 6455**, em dezembro de 2011. O SSE parecer "mais simples" não é um retrofit de design — ele veio primeiro, e o WebSocket foi construído depois, especificamente para o caso de mão dupla que o SSE nunca se propôs a resolver.

## 11. "Entrega exatamente uma vez" não existe — este sistema consegue o mesmo efeito combinando duas garantias mais antigas

O RabbitMQ (como todo message broker antes dele, remontando a ferramentas dos anos 1990 como o IBM MQSeries) só consegue realmente prometer entrega **pelo menos uma vez** através da rede — uma reentrega após uma queda ou um ack perdido é sempre possível. Este sistema nunca tenta evitar isso; em vez disso, todo consumidor é idempotente (descoberta 2), então um evento reentregue é processado com segurança em vez de nunca ser entregue. "Entrega pelo menos uma vez + um consumidor idempotente" é a receita de fato, com décadas de idade, geralmente vendida como "exatamente uma vez" — não há nenhum truque de mensageria por trás disso, só uma duplicata que silenciosamente não faz nada na segunda vez.

## 12. Os subcharts Helm do `orchestration` são a convenção de "umbrella chart", não uma estrutura específica de cinco serviços

O `orchestration/Chart.yaml` declara a pasta `/k8s` de cada serviço como uma dependência de subchart (`file://../catalog-api/k8s`, e assim por diante), compondo cinco charts versionados de forma independente em um único release implantável. Essa é a convenção de **umbrella chart** do próprio Helm, documentada há muito tempo e em uso desde a era do Helm v2 (a documentação da comunidade sobre dependências de chart remonta a ~2016) exatamente por esse motivo: deixar cada componente versionar e ser templado de forma independente, e um chart "pai" declarar "estes, juntos, são o release" — o arquivo de workspace raiz de um monorepo, só que para manifests do Kubernetes em vez de pacotes npm.

## 13. `containerPort: 8080` em todo lugar não é uma convenção do projeto — é uma fronteira de segurança do Unix dos anos 1980

Todo Dockerfile de serviço roda como um `USER app` não-root e escuta na porta `8080` (`ASPNETCORE_URLS=http://+:8080`), enquanto a única coisa vinculada à porta `80` no host é o controlador de ingress. Portas abaixo de 1024 são a **faixa privilegiada** do Unix — vincular uma delas exige root (ou, no Linux moderno, a capability `CAP_NET_BIND_SERVICE`) desde o 4.2BSD, no início dos anos 1980, décadas antes de containers existirem. Rodar os containers de aplicação como não-root é uma escolha deliberada de menor privilégio, e a `8080` — a porta convencional "http-alt" — é simplesmente o número não-privilegiado para o qual todo serviço recai como consequência; ela não é coordenada com a porta 80 do próprio Ingress, é só o número que todo serviço acaba compartilhando porque todos esbarram na mesma barreira do sistema operacional. O próprio Ingress consegue se vincular à porta 80 porque seu container legitimamente precisa de root (ou da capability) para responder na porta bem conhecida — e é também por isso que só ele, e mais nada no cluster, faz isso.

O formato mais amplo aqui — um gateway na frente da porta bem conhecida, cada backend atrás dele em uma porta alta arbitrária — é o padrão **reverse proxy**, mais antigo que o Ingress do Kubernetes em décadas (nginx e Apache já faziam exatamente isso nos anos 1990, e a ideia por trás — um único endereço que o mundo externo alcança, com as requisições despachadas atrás dele — é ainda mais antiga). "Ingress" é só o nome que o Kubernetes dá a um reverse proxy que entende Services do Kubernetes.

Conferido ao vivo, não apenas assumido: o controlador de Ingress aqui nem chega a tomar o caminho "root" dessa alternativa. `kubectl get deployment ingress-nginx-controller -n ingress-nginx -o jsonpath='{.spec.template.spec.containers[0].securityContext}'` retorna `runAsNonRoot: true`, `runAsUser: 101` e `capabilities: {add: ["NET_BIND_SERVICE"], drop: ["ALL"]}` — um processo genuinamente não-root, com toda capability do Linux removida exceto a única de que ele realmente precisa para se vincular às portas 80/443. Esse é o próprio manifesto do projeto upstream `kubernetes/ingress-nginx`, aplicado tal como vem (não escrito para este projeto), e é a resposta de livro-texto para "como vincular uma porta privilegiada sem dar root completo a um processo": remover tudo, devolver exatamente uma capability. O encaminhamento de porta do próprio Docker (`extraPortMappings` no `orchestration/kind/cluster-config.yaml`, mapeando a porta 80 real do host para dentro do container que faz o papel de nó do `kind`) é a outra metade do caminho que uma requisição do navegador a `http://localhost` de fato percorre — essa parte roda no nível do daemon do Docker, já privilegiado no host em qualquer instalação Docker, sem relação com nada que os próprios containers deste projeto façam.

## 14. A separação liveness/readiness do Kubernetes junta duas ideias bem mais antigas, não é uma invenção do Kubernetes

O Deployment de cada serviço (ex.: `orders-api/k8s/templates/deployment.yaml`) declara um `readinessProbe` e um `livenessProbe` contra o mesmo endpoint `/health`, verificados em cronogramas independentes (`periodSeconds: 5` e `10`). As duas perguntas que eles respondem são, na verdade, duas ideias bem mais antigas, separadas, às quais o Kubernetes só deu um contrato HTTP compartilhado. **Readiness** — esta instância deve receber tráfego agora — é a mesma pergunta que o health check de um load balancer faz desde pelo menos os anos 1990: um balanceador L4/L7 tira um backend de rotação no momento em que ele para de responder, e o recoloca no momento em que volta a responder. **Liveness** — esta instância deve ser derrubada e substituída — é a ideia de "deixe quebrar e seja reiniciado por um supervisor", das **árvores de supervisão** do Erlang/OTP, descritas por Joe Armstrong em seu doutorado de 1996/2003 na Ericsson como o mecanismo central de tolerância a falhas por trás da confiabilidade do OTP, ela mesma baseada em prática interna da Ericsson em comutadores de telecomunicações desde meados dos anos 1980. O Kubernetes não inventou nenhuma das duas perguntas — só padronizou ambas como um contrato de polling HTTP que qualquer container pode implementar.

## 15. Os campos `@tr`/`@sp` em cada linha de log são a ideia de décadas do Dapper, não um recurso do Serilog

Toda linha de log de requisição neste sistema carrega um `@tr` (trace ID) e um `@sp` (span ID) — o mesmo valor de `@tr` atravessa a busca de preço no catálogo, o log de criação do pedido e o log de conclusão da requisição como uma única cadeia causalmente ligada, para uma chamada `POST /api/orders`. Nenhum `Program.cs` de serviço define esses campos explicitamente (`orders-api/src/FiapGames.Orders.Api/Program.cs:16-26` só conecta o `Serilog.Formatting.Compact.CompactJsonFormatter` ao console) — o formatter apenas expõe o que já está em `Activity.Current`, e o ASP.NET Core cria automaticamente uma `Activity` por requisição recebida desde o .NET Core 3.0, seguindo o padrão **W3C Trace Context** (uma Recomendação do W3C desde 2020). A ideia por trás — marcar uma unidade de trabalho com um trace ID compartilhado por todo serviço que ela atravessa, mais um span ID restrito a cada salto — é o **Dapper** do Google, descrito em um artigo de 2010 como a infraestrutura de rastreamento por trás dos próprios serviços de produção do Google; a mesma linhagem produziu o Zipkin do Twitter (2012) e, eventualmente, o projeto OpenTelemetry, que fundiu OpenTracing e OpenCensus em 2019. Nada aqui se autodenomina "OpenTelemetry", mas o par trace/span em cada linha de log é o mesmo mecanismo — só consumido direto nos logs em vez de um backend de rastreamento dedicado.

## 16. O Kubernetes não faz rede nenhuma sozinho — um CNI plugável separado faz isso, e trocá-lo mudou o comportamento de verdade

Todo pod neste cluster recebe um endereço IP real e consegue alcançar o IP de qualquer outro pod diretamente — mas o próprio Kubernetes nunca implementa isso. Ele delega inteiramente a um plugin **CNI** (Container Network Interface): um software separado, responsável por de fato conectar a rede dos pods, que o Kubernetes apenas invoca no momento de criar cada pod. O `kind` já vem com um padrão bem simples chamado `kindnet`, que cuida da conectividade básica pod-a-pod e nada além disso — criticamente, ele ignora silenciosamente qualquer recurso `NetworkPolicy` no cluster. Um `NetworkPolicy` não é uma regra de firewall imposta pelo Kubernetes; é mais parecido com um pedido, que só significa algo se o CNI por baixo souber lê-lo e aplicá-lo. Isso foi conferido diretamente (na própria documentação do Calico) antes de confiar nisso, em vez de simplesmente assumido, e depois provado ao vivo: trocando o `kindnet` pelo Calico e testando o exato mesmo YAML de `NetworkPolicy` antes e depois — um pod de depuração com o label de `frontend` deu timeout ao tentar alcançar `postgres:5432` sob o Calico, e teria se conectado instantaneamente sob o `kindnet`, mesmo com o arquivo de política nunca tendo mudado. A regra sempre esteve "correta"; só o plugin por baixo decidia se alguém de fato a lia.

Essa mesma camada de rede do cluster também é o motivo de uma variável de ambiente de um `Deployment` poder dizer `RabbitMq__Host: rabbitmq` — um nome puro, sem nenhum endereço IP em lugar nenhum — e simplesmente funcionar. Todo `Service` do Kubernetes ganha automaticamente um nome DNS estável, resolvido pelo **CoreDNS**, um servidor DNS interno ao cluster que o Kubernetes roda exatamente para isso (`<service>.<namespace>.svc.cluster.local`, com `<service>` sozinho resolvendo dentro do mesmo namespace via os domínios de busca padrão do pod). Confirmado ao vivo com um pod de depuração descartável: `nslookup kubernetes.default.svc.cluster.local` retornou o ClusterIP interno do próprio servidor da API, e uma busca externa (`nslookup raw.githubusercontent.com`) resolveu normalmente também — a mesma instância do CoreDNS cuida tanto da descoberta de serviços interna ao cluster quanto do DNS comum da internet, encaminhando esse último para frente.

## 17. "Remover toda capability do Linux" quebrou o Postgres e o RabbitMQ — uma lição ao vivo sobre um padrão de décadas do Docker

**Root** no Linux não é um privilégio único e indivisível — é um conjunto de dezenas de **capabilities** concedidas separadamente (`CAP_NET_BIND_SERVICE` para vincular uma porta abaixo de 1024, `CAP_CHOWN` para mudar o dono de um arquivo, `CAP_SETUID`/`CAP_SETGID` para mudar qual usuário ou grupo um processo roda, e por aí vai). Um container pode rodar como UID 0 e ainda assim não conseguir fazer quase nada do que o root tradicionalmente conseguia, se as capabilities por trás dessas ações específicas tiverem sido removidas — remover todas e devolver exatamente uma (como o controlador de Ingress deste projeto faz com `CAP_NET_BIND_SERVICE`, veja a entrada acima sobre portas privilegiadas) é um meio-termo real e significativo entre "root completo" e "nenhum privilégio", não só uma formalidade.

Este projeto tentou remover toda capability de todo container de forma uniforme, `postgres`/`rabbitmq` incluídos — e quebrou os dois na hora: `chmod: /var/run/postgresql: Operation not permitted` do Postgres, `su-exec: setgroups: Operation not permitted` do RabbitMQ. As duas imagens oficiais seguem uma convenção do Docker extremamente comum, muitas vezes só chamada de **padrão "entrypoint"**: o primeiro processo do container começa como root, faz alguma configuração que só o root consegue fazer (aqui, corrigir a posse de um volume de dados montado), e só então **rebaixa** para um usuário sem privilégios via uma ferramenta como `gosu` ou `su-exec` antes de de fato iniciar o servidor de verdade — o próprio processo do Postgres nunca roda como root, mas a breve janela como root na inicialização, sim. Esse próprio passo de rebaixamento precisa de `CAP_CHOWN` (para corrigir a posse) e `CAP_SETUID`/`CAP_SETGID` (para de fato virar o usuário sem privilégios), que uma remoção geral de capabilities tira junto com tudo o mais, quebrando o padrão antes mesmo de chegar na parte em que ele se torna seguro. Os sete containers de aplicação deste próprio projeto são imagens simples, de processo único, construídas sob medida, sem nenhuma dança de entrypoint desse tipo — motivo exato pelo qual remover toda capability foi seguro para os sete, e não para as duas imagens prontas fazendo algo mais elaborado na inicialização.

## 18. A papelada de um release do Helm mora em um "namespace" diferente dos recursos que ele cria — a mesma palavra, dois significados sem relação

Todo `Deployment`/`Service`/`Secret` que este chart renderiza cai no namespace `fiap-games` — isso é controlado por um campo `namespace:` embutido em cada template, vindo de `.Values.global.namespace`. Separadamente, e sem nenhuma relação com isso, o Helm mantém sua **própria** papelada do release em si — literalmente um `Secret` do Kubernetes (com um nome tipo `sh.helm.release.v1.fiap-games.v6`) guardando o que foi implantado por último e o histórico de revisões — armazenado onde quer que `-n`/`--namespace` tenha apontado no comando `helm install`/`helm upgrade` que o criou. O próprio `helm install fiap-games .` do `GETTING_STARTED.md` nunca passa `-n` nenhum, então esse registro foi parar em qualquer que seja o namespace padrão do contexto atual do `kubectl` — neste cluster, literalmente o namespace chamado `default`.

São duas configurações que por acaso se chamam "namespace" as duas, apontando para dois lugares sem relação — parecido com uma biblioteca onde a ficha de catálogo de um livro fica arquivada sob um número de prateleira, enquanto o livro em si está sentado numa prateleira completamente diferente. Os próprios exemplos do `DEPLOY_VERIFICATION.md` erraram isso por um tempo: `helm upgrade fiap-games . -n fiap-games` diz ao Helm "vá procurar a papelada do release `fiap-games` *dentro do namespace `fiap-games`*" — mas a papelada nunca esteve lá, ela está no `default`. O Helm procurou, não achou nada, e recusou com `Error: UPGRADE FAILED: "fiap-games" has no deployed releases`, mesmo com os pods de verdade rodando bem ali no `fiap-games` o tempo todo. `helm list -A` é o que de fato revela onde a papelada de um release mora, na dúvida, em vez de assumir que bate com o namespace pra onde seus recursos são renderizados.

## Glossário

- **ACID** — Atomicidade, Consistência, Isolamento, Durabilidade: as quatro garantias de uma única transação de banco de dados; uma Saga existe justamente porque uma transação de negócio entre serviços não consegue as quatro de graça.
- **Anti-Corruption Layer (ACL)** — um padrão de DDD: uma fronteira de tradução que impede o modelo de um sistema externo de vazar para o modelo do seu próprio domínio.
- **Coreografia** — coordenar um processo multi-serviço sem um coordenador central; cada serviço reage a eventos por conta própria.
- **CNI (Container Network Interface)** — o componente plugável de fato responsável pela rede dos pods no Kubernetes; o próprio Kubernetes delega a qualquer um que esteja instalado, e nem todo CNI aplica `NetworkPolicy` (ver descoberta 16).
- **CoreDNS** — o servidor DNS que o Kubernetes roda dentro do cluster, resolvendo nomes de Service para endereços internos estáveis e encaminhando buscas comuns de internet para frente (ver descoberta 16).
- **Dapper** — o artigo de 2010 do Google sobre rastreamento distribuído: marcar uma unidade de trabalho com um trace ID compartilhado por todo serviço que ela atravessa, mais um span ID por salto, para que uma requisição possa ser seguida entre fronteiras de serviço; ancestral do Zipkin, do Jaeger e do OpenTelemetry.
- **DIP (Dependency Inversion Principle)** — o "D" do SOLID: código de alto nível deve depender de abstrações, não de implementações concretas de baixo nível.
- **Release do Helm** — o registro de papelada do próprio Helm sobre a implantação de um chart (o que está instalado, histórico de revisões), guardado como um `Secret` em qualquer namespace que o comando `helm` tenha mirado — independente de, e não necessariamente igual a, o namespace para onde os próprios recursos do chart são renderizados (ver descoberta 18).
- **Hexagonal Architecture** — o estilo arquitetural de Alistair Cockburn, de 2005: a regra de negócio fica no centro, isolada de frameworks e infraestrutura por portas e adaptadores.
- **Idempotente** — uma operação que produz o mesmo resultado aplicada uma vez ou várias; vem da álgebra abstrata do século XIX, não da computação.
- **IETF / RFC** — a Internet Engineering Task Force e seus documentos de padrão numerados (Request for Comments) — o processo que produziu JWT, OAuth 2.0 e WebSocket como padrões abertos e neutros de fornecedor.
- **Capability do Linux** — uma das dezenas de permissões concedidas individualmente que compõem o que chamamos de "root" (`CAP_CHOWN`, `CAP_NET_BIND_SERVICE`, `CAP_SETUID` etc.); um processo pode rodar como root e ainda assim não ter a maioria delas, se forem explicitamente removidas (ver descoberta 17).
- **NetworkPolicy** — um recurso do Kubernetes que descreve quais pods podem enviar tráfego para quais outros pods; só é tão significativo quanto o CNI que o aplica (ver descoberta 16).
- **Mônada Either** — um tipo de programação funcional que representa "um entre dois resultados" (normalmente sucesso/falha), sem lançar exceção; `Result<T>` é essa ideia com um nome amigável ao mundo orientado a objetos.
- **Orquestração (neste contexto)** — coordenar um processo multi-serviço por meio de um coordenador central que diz explicitamente a cada participante o que fazer em seguida.
- **Índice parcial** — um índice de banco de dados que cobre apenas as linhas que atendem a uma condição `WHERE`, permitindo que uma constraint valha para um subconjunto de uma tabela, não para ela inteira.
- **Porta privilegiada** — uma porta TCP/UDP abaixo de 1024; vincular uma delas exige root (ou uma capability específica do SO) desde os primórdios do Unix, uma convenção ainda aplicada por todo sistema operacional moderno.
- **Reverse proxy** — um servidor que fica na frente de um ou mais servidores backend, repassando as requisições dos clientes até eles; o Ingress do Kubernetes é um reverse proxy que entende Services do Kubernetes.
- **Saga** — uma transação de negócio que atravessa múltiplos serviços, implementada como uma sequência de transações locais com (opcionalmente) um passo compensatório para cada uma.
- **SSE (Server-Sent Events)** — um mecanismo de push via HTTP, de mão única, do servidor para o navegador (`text/event-stream`), mais antigo que o WebSocket como padrão de navegador.
- **Árvore de supervisão** — o mecanismo de tolerância a falhas do Erlang/OTP: um processo supervisor reinicia um filho que falhou, em vez de tentar impedir toda falha possível; o modelo por trás do liveness probe do Kubernetes.
- **Transactional Outbox** — gravar uma mensagem de saída em uma tabela dentro da mesma transação de banco de dados da mudança de negócio que ela descreve, para que um processo separado a publique de forma confiável depois.
- **Transação compensatória** — o passo de "desfazer" que uma Saga executa se uma etapa posterior falhar, para reverter o efeito de uma etapa anterior; a saga deste projeto não precisa de uma (ver descoberta 5).
- **W3C Trace Context** — o padrão do W3C (uma Recomendação desde 2020) para propagar um trace ID e um span ID entre chamadas de serviço; o ASP.NET Core o implementa automaticamente via `Activity`, sem exigir código de aplicação.
